# StudyFlow Module Interface

This document defines the public interfaces for the JavaScript service modules. It is the shared contract for implementation and integration. Function names, parameters, return types, and stored fields should not be changed without informing the team.

## General conventions

- All public functions listed here must be exported from their service file.
- `username` is entered by the student and is the unique account/login identifier.
- `courseId`, `taskId`, and `sessionId` are generated by the system.
- A single-object lookup returns `null` when the requested object does not exist; list queries return `[]` when there are no matches.
- A command returning `boolean` reports whether the operation succeeded.
- `estimatedDuration` remains `null` when omitted. A fallback duration
  of 2 hours is used only when calculating remaining workload.
- `taskStatus`, `priority scores`, `remaining workload`, and `workload warnings` are derived values and must not be stored in task records.
- Date-time values (including deadlines and session boundaries) are ISO 8601 strings, durations are measured in hours, and progress is stored as one of `0`, `25`, `50`, `75`, or `100`.
- A task is completed when `completed === true || currentProgress === 100`; incomplete means `!completed && currentProgress < 100`. Apply this consistently to ranking, overdue queries, warnings, and new scheduling.
- Domain validation belongs to the relevant service; UI confirmation and HTML updates belong to page scripts/components.
- The result columns below describe successful result values. Data-access functions explicitly return Promises. Whether higher-level services return a value directly or `Promise<T>` must be verified against their implementation; a service that awaits API data returns `Promise<T>`. Null/boolean results do not define network-error handling.

## Shared return type

Authentication commands produce an `OperationResult` (or resolve to it when asynchronous):

```ts
type OperationResult = {
  success: boolean;
  message: string;
  student: Student | null;
};
```

## `storageService.js`

Provides a common endpoint-based data-access interface used by StudyFlow service modules. This contract does not assume a particular backend or browser persistence mechanism.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `get(endpoint)` | `endpoint: string` | `Promise<any>` | Read and parse data from the specified endpoint/query. |
| `post(endpoint, body)` | `endpoint: string`, `body: object` | `Promise<any>` | Send a create request with the supplied body to the endpoint. |
| `put(endpoint, body)` | `endpoint: string`, `body: object` | `Promise<any>` | Send an update request with the supplied body to the endpoint. |
| `del(endpoint)` | `endpoint: string` | `Promise<void>` | Delete a record at the specified endpoint. |

## `authService.js`

Manages registration, authentication, password reset, and the current login session.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `register(studentName, username, password, confirmPassword)` | 4 strings | `OperationResult` | Validate registration input, ensure the username is unique, create a new student account. |
| `login(username, password)` | 2 strings | `OperationResult` | Authenticate a student and establish the current authenticated session. |
| `resetPassword(username, newPassword, confirmPassword)` | 3 strings | `OperationResult` | Validate the username, new password, and confirmation, then update the student's stored password. |
| `logout()` | None | `void` | End the current authenticated session. |
| `getCurrentUser()` | None | `Student \| null` | Return the authenticated student or `null` if no valid session exists. |

## `courseService.js`

Manages course records belonging to students.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `createCourse(course)` | `course: object` | `Course` | Validate the input, generate `courseId`, and create a course. |
| `getCoursesByStudent(username)` | `username: string` | `Course[]` | Return all courses belonging to the specified student. |
| `getCourseById(courseId)` | `courseId: string` | `Course \| null` | Return the course with the specified ID, or `null` if it does not exist. |
| `updateCourse(courseId, data)` | `courseId: string`, `data: object` | `Course \| null` | Update only `courseName` and/or `color` while preserving `courseId` and `username`. |
| `deleteCourse(courseId)` | `courseId: string` | `boolean` | Delete the course, all its tasks, and CalendarSessions linked to those tasks (cascade requirement). |

### Course creation input

The `course` object contains:

- `username`
- `courseName`
- `color` (optional; defaults to `null`)

The service generates `courseId`. It must not add fields that are not defined in the data contract.

## `taskService.js`

Manages task CRUD operations, progress updates, completion, and task queries.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `createTask(taskData)` | `taskData: object` | `Task` | Validate the input, generate `taskId` and `createdAt`, and create a task record. |
| `getTasksByStudent(username)` | `username: string` | `Task[]` | Return all tasks from courses belonging to the specified student. |
| `getTasksByCourse(courseId)` | `courseId: string` | `Task[]` | Return all tasks belonging to the specified course. |
| `getTaskById(taskId)` | `taskId: string` | `Task \| null` | Return the task with the specified ID, or `null` if it does not exist. |
| `updateTask(taskId, data)` | `taskId: string`, `data: object` | `Task \| null` | Update permitted task fields while preserving `taskId`, `courseId`, and `createdAt`. |
| `deleteTask(taskId)` | `taskId: string` | `boolean` | Delete the task and all CalendarSessions linked to it (cascade requirement). |
| `updateTaskProgress(taskId, currentProgress)` | `taskId: string`, `currentProgress: number` | `Task \| null` | Update progress to an allowed value and set `completed` to whether progress is `100` (proposed synchronization rule). Task status remains derived. |
| `markCompleted(taskId)` | `taskId: string` | `Task \| null` | Set `currentProgress` to `100` and `completed` to `true` (proposed synchronization rule). |
| `getOverdueTasks(username)` | `username: string` | `Task[]` | Return all incomplete tasks whose deadlines have passed from courses belonging to the specified student. |

### Task creation input

The `taskData` object contains:

- `courseId`
- `taskName`
- `description` (optional; defaults to `""`)
- `deadline`
- `importance` (defaults to `"medium"`)
- `estimatedDuration` (optional; remains `null` when omitted)
- `currentProgress` (defaults to `0`)

The service generates `taskId` and `createdAt`. `completed` defaults to whether initial `currentProgress` is `100`.

### Task update and completion rules

- `deadline` contains both date and time. Overdue queries compare the exact deadline with the current time.
- Editable task fields are `taskName`, `description`, `deadline`, `importance`, `estimatedDuration`, and `currentProgress`; generated IDs, course ownership, and creation time remain unchanged.
- Under the proposed synchronization rule, progress updates also update `completed`; lowering progress below `100` reopens the task. Apply the same rule through `updateTask()` when it changes progress.
- Existing records are still evaluated with the shared completion predicate. The current source must be checked before replacing any existing independent completion-toggle behavior.
- Course and task deletion require UI confirmation before invoking the service and must remove linked calendar sessions.

Derived values such as `taskStatus`, `remainingWorkload`, `urgencyScore`, `importanceScore`, `workloadScore`, `priorityScore`, and workload warnings are not stored in task records.

## `priorityService.js`

Calculates priority-related task values, ranks non-completed tasks, and provides global and local task recommendations.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `getUrgencyScore(deadline)` | `deadline: string \| Date` | `number` | Compare the exact deadline with the current time first; otherwise use the calendar-day urgency ranges defined in the Data Contract. |
| `getImportanceScore(importance)` | `importance: string` | `number` | Convert an importance level into its numeric score. |
| `calculateRemainingWorkload(task)` | `task: Task` | `number` | Calculate remaining workload using the task's `estimatedDuration`, or a fallback duration of 2 hours when it is `null`. |
| `getWorkloadScore(remainingWorkload)` | `remainingWorkload: number` | `number` | Convert remaining workload into its numeric workload score. |
| `calculatePriority(task)` | `task: Task` | `number` | Calculate `0.6 * urgency + 0.25 * importance + 0.15 * workload`. |
| `rankTasks(tasks)` | `tasks: Task[]` | `Task[]` | Exclude completed tasks and return the remaining tasks in priority ranking order without storing calculated values. |
| `getGlobalRecommendation(tasks)` | `tasks: Task[]` | `Task \| null` | Return the highest-ranked non-completed task from the student's tasks. |
| `getLocalRecommendation(tasks)` | `tasks: Task[]` | `Task \| null` | Return the highest-ranked non-completed task from the tasks belonging to one course. |

### Remaining workload

If `estimatedDuration` is provided:

`remainingWorkload = estimatedDuration * (1 - currentProgress / 100)`

Otherwise, the service uses the 2-hour fallback:

`remainingWorkload = 2 * (1 - currentProgress / 100)`

The fallback duration is used only during calculation. The stored `estimatedDuration` remains `null`.

### Ranking order

Completed tasks are excluded from recommendation ranking. Overdue tasks remain eligible for ranking and receive the corresponding urgency score.

Tasks are sorted by:

1. Priority score: descending.
2. Deadline: ascending.
3. Importance score: descending.
4. Created time: ascending.

### Recommendation scope

The caller supplies only the authenticated student's tasks for global recommendations, or tasks from one selected course for local recommendations. A recommendation returns `null` when no incomplete task is available.

## `workloadWarningService.js`

Detects workload risk for non-completed tasks and generates warning notifications when a task becomes risky.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `hasWorkloadWarning(task)` | `task: Task` | `boolean` | Determine whether a task meets the workload-warning condition using its urgency and workload scores. |
| `getWarningNotification(task)` | `task: Task` | `WarningNotification \| null` | Return a warning notification for a risky task, or `null` if no workload warning applies. |

### Workload warning rule

`hasWorkloadWarning(task)` is true only when all conditions hold:

- The task is incomplete (`!completed && currentProgress < 100`).
- The exact deadline has not passed.
- `estimatedDuration != null`.
- `(urgencyScore >= 80 && workloadScore >= 60) || (urgencyScore >= 60 && workloadScore >= 80)`.

Completed tasks receive no warning. Overdue incomplete tasks are displayed separately as overdue, even when no estimated duration is provided; `hasWorkloadWarning()` returns false for them.

The service reuses `getUrgencyScore()`, `calculateRemainingWorkload()`, and `getWorkloadScore()` from `priorityService.js`. The 2-hour fallback remains available for priority calculations but does not make a task with a missing estimate eligible for a workload warning.

### WarningNotification

`getWarningNotification(task)` returns `null` unless `hasWorkloadWarning(task)` is true. Otherwise it returns:

| Field | Type | Meaning |
| --- | --- | --- |
| `taskName` | `string` | Name of the task with a workload warning. |
| `deadline` | `string` | Exact deadline as an ISO 8601 date-time string. |
| `remainingWorkload` | `number` | Remaining estimated hours. |
| `message` | `string` | Warning displayed to the student. |

The payload is calculated at runtime and is not stored. Overdue labels use the Task record separately. `taskName` is retained from the supplied interface; verify the actual returned payload in code.

### Combined warning list

The supplied document mentions `getWorkloadWarning(tasks)` but does not list its export. The following is the proposed interface, pending code verification:

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `getWorkloadWarning(tasks)` | `tasks: Task[]` | `Task[]` (proposed) | Include overdue incomplete tasks and tasks with workload warnings, without duplicates, in the display order below. |

1. Overdue incomplete tasks first, then workload-warning tasks.
2. Urgency score descending within each group.
3. Workload score descending when urgency scores tie.

Completed tasks are excluded. No further tie-break is specified. An overdue task without an estimate may use the 2-hour fallback for sorting; its inclusion is based on overdue status. The proposed list contains Task records, not WarningNotification objects. If the current UI builds this list itself, document that responsibility instead of inventing an existing service export.

## `calendarService.js`

Manages manual drag-and-drop study sessions for the authenticated student.

| Function | Parameters | Expected result value | Responsibility |
| --- | --- | --- | --- |
| `getSchedules()` | None | `CalendarSession[]` | Return all scheduled sessions for the logged-in student. |
| `createSchedule({ taskId, startTime, endTime })` | `object` | `CalendarSession` | Validate the task and session times, generate `sessionId`, and create a CalendarSession. |
| `getScheduleByTaskId(taskId)` | `taskId: string` | `CalendarSession[]` | Return all sessions linked to `taskId`. |
| `updateSchedule(sessionId, changes)` | `sessionId: string`, `changes: object` | `CalendarSession` | Validate and update an existing session while preserving `sessionId`. |
| `deleteSchedule(sessionId)` | `sessionId: string` | `void` | Delete a scheduled session by ID without deleting or changing its task. |

### Calendar scheduling rules

- An authenticated student must exist (`getCurrentUser() != null`).
- The task must exist and belong to that student through its course.
- Only incomplete tasks (`!completed && currentProgress < 100`) may be newly scheduled. Both pending and overdue tasks remain eligible.
- An overdue task may be scheduled after its deadline so the student can plan when to finish it.
- `startTime` and `endTime` must be valid ISO 8601 date-time strings, and `endTime` must be strictly later than `startTime`.
- An updated session must exist, belong to the current student, and retain its `sessionId`. Any changed task reference or time range must be validated.
- Creating, moving, resizing, or deleting a session does not change the task deadline, progress, or completion state.
- A task may have zero or many sessions; an empty session query returns `[]`.
- Deleting a task or course removes the linked sessions as specified in the Data Contract. Existing-session behavior when a task is completed is not defined by the supplied documents and remains to be checked in code.
